Key-value Database systemdesignschool.io/fundamentals/key-value-database NoSQL databases optimize for different access patterns. The simplest pattern is direct key- value lookup. Many applications need only this operation: session storage, caching, user preferences. Why Key-Value Databases Exist In the original Dynamo paper, Amazon engineers identified a pattern: Many services on Amazon's platform only need primary-key access to a data store. Services providing best seller lists, shopping carts, customer preferences, session management, sales rank, and product catalog use relational databases inefficiently. This pattern limits scale and availability. Dynamo provides a simple primary-key only interface to meet these requirements. 1/3

Key-value databases are the simplest NoSQL type. The interface resembles a hashmap. Store values by key. Retrieve values by key. That's it. How Key-Value Databases Work The data model couldn't be simpler. Each record has two parts: a unique key and a value. The database provides three operations: get(key), put(key, value), and delete(key). No schemas. No relationships. No joins. This simplicity enables performance. Primary key lookups are fast. The database can hash the key to find the exact location. No table scans. No index traversals. Typical latency measures in microseconds. Horizontal scaling is straightforward. Partition data by key ranges or hash values. Add more servers to increase capacity. Each server handles a subset of keys. The partitioning logic remains simple because queries never span partitions. The API matches programming language dictionaries. Developers already understand get and put. No SQL to learn. No ORM complexity. Application code and database model align naturally. When to Use Key-Value Databases High-performance reads and writes benefit from key-value simplicity. Reading and writing with a key is a fast operation. Applications demanding high-speed operations choose key-value stores. Simple data structures fit naturally. Customer details, webpages keyed by URL, shopping-cart contents, product categories, and e-commerce product details work well. Each entity needs independent access without relationships. Basic query requirements match key-value capabilities. Applications that don't need complex queries or frequent updates across multiple records work well. Simple data storage and retrieval operations are ideal. Popular Key-Value Databases Because of their performance and simplicity, key-value databases rank highly in popularity according to db engine ranking. 2/3

Redis and DynamoDB lead the category. Redis specializes in in-memory caching with microsecond latency. DynamoDB provides durable, distributed storage with single-digit millisecond latency. Real-World Examples Dropbox stores file metadata in DynamoDB through their Alki system. Each file's metadata maps to a unique file ID. No relationships between files matter. Simple key-value lookups provide the speed needed. This saved Dropbox millions in infrastructure costs compared to their previous on-premises storage. Snapchat stores Stories in DynamoDB. Story ID maps to content metadata. Stories don't relate to each other. Ephemeral nature matches key-value simplicity. Snap handles over 10 million queries per second and reduced median latency by 20%. Disney+ uses DynamoDB for content metadata and user interactions. Video ID maps to title, description, and thumbnail URL. Each video loads independently. They ingest billions of customer actions daily for features like watchlists and personalized recommendations. 3/3
