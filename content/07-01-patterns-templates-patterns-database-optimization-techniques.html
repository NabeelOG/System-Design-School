Database Optimization Techniques systemdesignschool.io/fundamentals/database-optimization A database query scans all 10 million rows to find orders for user 12345. Response time is 8 seconds. Users abandon the page. An optimized database uses indexes, sharding, replication, and tiered storage to answer the same query in 10 milliseconds. After you design the data model, you optimize how the database stores and retrieves that data. An unoptimized database forces full table scans for every query. An optimized database handles millions of queries per second. Indexing An index creates a fast lookup structure so queries avoid scanning the entire table. Without an index on user_id, the query SELECT * FROM orders WHERE user_id = 12345 scans every row. With an index, the database jumps directly to rows for that user using a B-tree structure. 1/4

If you frequently query by user_id, create an index on that column. A multi-column index (also called a composite index) speeds up queries that filter on multiple fields together. If you frequently query by user_id and status, create an index on (user_id, status). The order matters: an index on (user_id, status) helps queries filtering on user_id alone or on both fields, but not queries filtering only on status. Indexes work best when they reduce the candidate set significantly. An index on user_id in a table with 1 million users works well because each user has few rows. An index on status with values active, inactive, pending works poorly because each value matches 33% of rows. The database still scans hundreds of thousands of rows. Indexes speed up reads but slow down writes. Every insert, update, or delete must update all relevant indexes. Only index fields critical to query performance. Use EXPLAIN to identify slow queries before adding indexes. In interviews, mention that over-indexing wastes memory and degrades write performance. Partitioning and Replication Database partitioning and replication are covered extensively earlier in the course. Partitioning splits data across multiple servers to handle more writes and storage. Replication copies data to multiple servers for availability and read scaling. These techniques are fundamental to scaling databases, but using them effectively requires additional optimizations covered here. 2/4

Cold and Hot Data Separation Hot data is accessed frequently. Cold data is accessed rarely. Storing both on the same fast, expensive storage wastes money. Separate them by access patterns. Hot/Cold Data Separation Today 30 days ago 1 year ago Access Frequency HOT DATA 90% of queries COLD DATA 10% of queries Hot Storage (Primary DB) 💾 SSD / NVMe Recent 30 days • Fast access • High cost Cold Storage (Archive) 🗄 S3 / HDD >30 days old • Slower access • Low cost Archive after 30 days Recent orders are hot data. Users check order status frequently in the first few days. Store recent orders on fast SSDs in the primary database. Orders older than 30 days are cold data. Users rarely view them. Archive cold orders to cheaper storage like HDDs or Amazon S3. The application checks the primary database for recent orders first. If not found, it queries the archive. This tiering reduces database size and improves performance. A smaller database fits more data in memory for caching. Cold data queries might be slower, but that is acceptable because they are rare. Query Optimization Beyond indexes, query optimization shapes how the database executes operations. Use EXPLAIN to understand query execution plans. A query that scans 1 million rows when it should scan 1,000 indicates missing indexes or poor query structure. 3/4

Instead of joining orders and customer tables on every query, store customer name directly in the orders table. Reads become faster. Writes become more complex because customer name updates must propagate to all orders. Use denormalization when read frequency far exceeds write frequency. Materialized views pre-compute expensive queries. A dashboard showing monthly sales by region recalculates aggregations on every load. A materialized view computes this once and stores results. Queries read the pre-computed view instead of scanning millions of rows. Refresh the view hourly or when source data changes. Interview Application When asked to design a database for a social network, mention indexing user lookups by user_id and posts by created_at. Reference partitioning and replication from earlier in the course for horizontal scaling. Focus on optimizations specific to the use case: denormalize user data into posts for faster timeline rendering, use materialized views for trending topics, separate hot and cold data by archiving posts older than one year. Explain trade-offs clearly. Indexes speed reads but slow writes. Denormalization improves read performance but complicates updates. Materialized views trade storage and refresh cost for faster queries. Cold storage reduces costs but increases latency for old data. Show you understand when each optimization applies and what it costs. 4/4
