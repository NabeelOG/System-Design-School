Each node lookup requires a separate disk read. Searching through a million-record database means potentially thousands of disk operations, each taking 5-10 milliseconds. What should be a microsecond operation becomes seconds of waiting. B-trees solve the disk access problem by packing hundreds of keys into each node. Instead of storing one key per node like binary trees, B-tree nodes contain 50-500 keys. A single disk read fetches an entire node, making each I/O operation maximally useful. This architectural change transforms database performance. MySQL's InnoDB engine uses B+ trees (a B-tree variant) as its primary storage structure. PostgreSQL similarly relies on B-tree indexes. Without B-trees, relational databases would be unusably slow on traditional storage. 1/5

B-trees maintain three critical properties: they stay balanced (all leaf nodes at the same depth), sorted (keys within nodes are ordered), and wide (nodes contain many keys). These properties ensure consistent performance regardless of data insertion patterns. Each order m B-tree has nodes containing between ⌈ m/2 ⌉ -1 and m-1 keys, except the root which can have as few as one key. This constraint ensures nodes stay between half-full and completely full, preventing degenerate cases that would hurt performance. The root node sits at the top and contains up to m-1 keys with m child pointers. Internal nodes contain keys plus pointers to child nodes. Keys within each node are sorted, allowing binary search within the node. Leaf nodes contain the actual data records along with their keys, and crucially, all leaves exist at the same tree depth. For database storage, typical B-tree orders range from 50 to 500, meaning each node contains dozens to hundreds of keys. This matches disk page sizes (4KB-16KB), maximizing the data retrieved per disk read. Search Operations Finding a record in a B-tree requires walking from root to leaf, using binary search within each node. For a tree with one million records and order 100, this means just 3-4 disk reads maximum. Each node access narrows the search space dramatically. 2/5

Insertion and Node Splitting B-tree insertions always happen at leaf nodes to maintain sorted order and consistent depth. When inserting into a non-full leaf, the operation simply places the new key in sorted position. However, when a leaf node becomes full (contains m-1 keys), node splitting occurs. 3/5

May create new root if splitting reaches the top Performance Impact • Splits are rare: only when nodes full • Most insertions: O(log n) + 1 write • Split insertions: O(log n) + up to log(n) writes (cascade up tree) • Keeps nodes 50-100% full 1 2 3 During splits, the node divides into two nodes, each containing ⌈ m/2 ⌉ -1 keys. The middle key promotes to the parent node. If the parent is also full, splitting cascades upward, potentially creating a new root and increasing tree height by one level. This splitting mechanism maintains the half-full guarantee while keeping the tree balanced. Modern databases optimize splits by maintaining pages that are 2/3 full rather than completely full, reducing split frequency during bulk insertions. Production Database Usage MySQL's InnoDB engine implements B+ trees (a B-tree variant where data resides only in leaves) for both primary and secondary indexes. The clustered index organizes table data in primary key order, while secondary indexes contain pointers back to the clustered index. PostgreSQL uses B-trees for most index types, with typical page sizes of 8KB containing 100- 200 index entries. PostgreSQL's implementation includes optimizations like right-link pointers between sibling pages to improve concurrent access patterns. File systems also rely on B-trees. ext4 uses extent trees (a B-tree variant) to track file block allocations efficiently. NTFS organizes directory entries and file allocation tables using B+ tree structures. 4/5
