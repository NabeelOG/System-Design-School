SSTables aren't complete database systems - they're the storage format that enables efficient binary search over large datasets. Modern distributed databases like Cassandra, RocksDB, and LevelDB use SSTables as their fundamental building blocks within larger storage engines. The File Format Problem Database storage engines need efficient file formats for persisting sorted data to disk. Simple approaches like CSV files require sequential scanning, making lookups O(n) for large datasets. Random access file formats can provide fast lookups but struggle with range queries and compression. SSTables solve this by combining sorted order with binary searchable indexes. The idea behind SSTables came from Google's BigTable project: store data in immutable, sorted files with sparse indexes. Once written, an SSTable never changes - updates and deletes are handled by creating new SSTables at the system level. This immutability enables aggressive caching, compression, and concurrent access without complex locking. SSTables provide the foundation for LSM trees, which handle the complete write path through memory buffers and multi-level compaction. Understanding SSTables as a file format helps explain why LSM-based systems achieve such high performance for both reads and writes. 1/4

SSTable File Format An SSTable file contains three main components: the sorted data section, a sparse index, and optional metadata. The data section stores key-value pairs in lexicographic order, enabling binary search algorithms. The sparse index contains every Nth key and its file offset, trading memory usage for lookup performance. Metadata includes compression algorithms, bloom filter data, and file statistics. Instead of indexing every key (which would consume enormous memory), SSTables index every 16KB or 64KB block. This reduces memory overhead while still enabling fast seeks to the approximate location of any key. Point queries use a two-step process: binary search the sparse index to find the approximate block, then binary search within that block to find the exact key. This approach provides O(log n) performance while using minimal memory for the index. Once you find the start position using the sparse index, you can sequentially scan until you reach the end of the range. This makes SSTables excellent for analytics workloads that need to process ranges of data. 3/4

Write Limitations and LSM Integration SSTables are immutable by design - they provide no write operations after creation. Adding new keys or updating existing ones requires creating entirely new SSTable files. This limitation is exactly why LSM trees exist: they provide the write path through memory buffers (memtables) and handle the complexity of managing multiple SSTable files. The immutable nature makes SSTables ideal building blocks for distributed systems. Files can be replicated, cached aggressively, and accessed concurrently without coordination. Multiple readers can access the same SSTable simultaneously, and the files can be safely copied or moved without affecting ongoing operations. When systems need to "update" data, they create new SSTables with newer values and rely on the read path to find the most recent version. Space reclamation and file management are handled by the storage engine's compaction processes, which merge multiple SSTables and delete obsolete files atomically. 4/4
